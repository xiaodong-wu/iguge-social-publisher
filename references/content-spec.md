# 内容与图片规范

## 事实来源

品牌为 iGuge healthy，面向营养品、功能食品、咖啡茶饮品牌、进口商、经销商和贴牌采购。
按实际产品区分粉剂、胶囊、片剂、软糖、液体、茶饮等，不把其他类目的属性套入本品。

逐条审查 `facts.declared`、`facts.corroborated`、`facts.variations` 和 `source_sections`。
重复出现只说明同页文字一致，不代表独立检测或验证。保留原文单位、MOQ、限定词；
表格中的三个月不自动换成九十天。单复数剂型可以规范表达，不把 softgel、capsule、
gummy 等不同剂型视为同义。原料名称保留对应来源，不猜测植物品种、提取比例或剂量。

可用文案事实通常是剂型、明确列出的原料、适用对象、MOQ、保质期及本品明示的
Private label / OEM / ODM 服务。成分列表不等于完整配方；“mushroom blend”不能扩写成
具体菌种或数量。没有定量证据不声称每份含量、高含量、高蛋白或特定浓缩倍数。
“natural”、类别名和包装外观不能证明 organic、vegan、sugar-free、allergen-free、
non-GMO、GMP、FDA approval、第三方检测、无副作用或任何市场准入。
价格、交期、产能、认证、保修和产地都需要该产品的可靠依据。

这是 B2B 选品推广，默认围绕可核对规格和采购讨论；不使用疾病预防/治疗、减重结果、
性能力、激素变化、认知改善或免疫增强等效果承诺，不写保证有效、百分百安全或服用建议。
网站 Function 字段、产品名和原包装上的营销表述都不构成效果证据。
`restricted_source_claims` 仅用于审阅，不放入文案、标签或新增图片文字。
标题含功效词时可保留足够辨识的中性名称，并保存原标题用于追溯；不靠改写掩盖实际规格冲突。

`discussion_sections` 中的 Formula、Sample、Packaging、FAQ 文本不是现货配置证明。
可以用“请确认所需包装/规格”这样的采购问题；不能将“discuss jars or sachets”写成
已默认供应罐装和袋装，或将“confirm caffeine specification”写成低咖啡因。
CTA 可以邀请客户带目标市场、数量和配方需求沟通；不暗示已获目的国批准。

产品标题、摘要、属性、正文存在原料、剂型、含量或 MOQ 的实质矛盾时拒绝候选；
模板讨论、单复数和旧 URL 名称不单独构成矛盾。没有依据的内容省略，不通过搜索
其他品牌商品或行业文章补出本品能力。`content-plan.json` 仅提供产品选题和采购方向。

## Facebook

80–150 个英文词，依次包含：

1. 四行 emoji 开头的已核实特点。可用 🌿、🍄、☕、🍵、🥤、💊、📦、✅、💡、🧪、🏭、🔬、🍫、🌱；图标本身也不得暗示不存在的材质或性能。
2. 一段简短的用途和采购价值，场景须受该产品证据支持。
3. 一句明确询盘 CTA。
4. 独占一行的完整规范产品 URL。
5. 8–12 个不重复且相关的英文标签。

## LinkedIn

150–250 个英文词，依次包含：

1. 专业的配方、剂型、品牌产品线或采购问题引入。
2. 3–5 条简明参数或功能要点，使用 `-` 或 `•`。
3. 一段已核实用途及买家价值。
4. 经销、批发、OEM/ODM 或贴牌询盘 CTA；具体供应能力需有对应来源。
5. 独占一行的完整规范产品 URL。
6. 3–5 个不重复的英文标签。

两个平台分别撰写，不能完全重复。面向品牌方、进口商、经销商和贴牌采购者。
应用场景须有产品依据，默认使用中性产品展示。以品牌方口吻直接表达有依据的产品信息，
不要把审核备注写成营销正文。避免反复使用 “are listed”“starting point”“product brief”
“for discussions”等空泛套话，也不要连续写多句确认、核对、同意规格的提醒。
确有未定规格时只保留一句必要说明；没有证据的卖点直接省略。
不编造客户反馈、个人体验、实拍经历或人工创作声明来制造真实感；自然表达不等于保证不被识别。
校验器按所有英文词计数（包括 URL 和标签中的英文词）；保持总数处于范围中间。

## 四宫格图片

只生成一张正方形图片，四个清晰分隔区域和干净间距。以真实主图为身份参考，
展示同一产品的互补画面：完整包装、中性棚拍、已可见的标签或容器细节、另一合理构图。
只有真实参考支持时才展示粉末、胶囊、茶包、冲泡液或内装物；不因类目名称虚构内容物。
保持包装形状、颜色、份量标识、瓶盖/封口、标签布局和可读品牌，不把罐改成袋或袋改成盒。
不新增不存在的原料、植物、包装、配件、认证徽章、功效标题、logo 或水印。
无背面参考不造营养成分表，无食品形态参考不编造颗粒或液体颜色；无需表现人物服用。
源图标签含未经核实的功效文字时，不放大强化；必要时用中性视角保留产品身份。

先用 `view_image` 查看主图，再加载 `imagegen`，将主图本地路径传给生成工具。
生成文件必须复制到运行目录后再交付，不把工具缓存作为唯一成品。

### 审核与有界恢复

允许合理灯光、反射、阴影、背景、透视和非功能性纹理差异。不能接受产品身份、包装结构、
剂型、清晰文字或品牌出错，也不能表现不受支持的操作。
初次生成后最多两次针对性修正；仍失败时再允许一次保留真实源产品、仅改变背景及布局
的四宫格合成。最多四次生成。失败则保留证据并停止；不换品绕过生成错误。

规范成品 `social.webp`：1:1，建议 1600×1600，最低 960×960，不大于 750 KiB；
压缩质量不低于 68，不放大小图凑尺寸。用像素重建移除 EXIF/XMP/ICC 等源元数据，
仅使用导出的文件上传。将优化脚本的实际输出保存为 `evidence/image-export.json`；
检查最终 WebP 与 JPEG，而不是仅检查生成工具的原图。JPEG 的 APP0/JFIF 格式头是正常
编码信息，不是 AI 标签；其他应用段和注释也须检查。保留生成原稿和内部来源记录。
上传副本 `social-upload.jpg`：同样正方形、最低 960×960、无元数据、不大于 750 KiB。
Facebook 和 LinkedIn 都上传此 JPEG，以保持浏览器上传兼容性。
双平台都核验成功前保留 JPEG 供安全续跑，之后可删除，规范 WebP 必须保留。
元数据清理、文案优化和平台 AI 披露是三件独立事项。不能据此承诺绕过平台识别、
移除已经写入帖子记录的标签或把生成图片说成实拍；披露设置见发布流程。

## 发布前审核记录

保存 `evidence/review.json`。如下为结构，填写真实结论和原文证据，不能把占位值当作通过：

```json
{
  "product_url": "实际规范产品URL",
  "source_review": "passed",
  "copy_review": "passed",
  "image_review": "passed",
  "claims": [
    {"claim": "文案特点", "quote": "source_sections 中的精确原文"}
  ],
  "image_attempts": 1,
  "image_versions": [],
  "accepted_minor_differences": [],
  "material_issues": [],
  "sha256": {
    "product_json": "实际SHA256",
    "source_hero": "实际SHA256",
    "facebook_copy": "实际SHA256",
    "linkedin_copy": "实际SHA256",
    "social_image": "实际SHA256",
    "social_upload": "实际SHA256"
  }
}
```

`claims` 至少四项，并覆盖两份文案中的全部技术、功能和供应能力断言。额外保存
`evidence/image-review.json` 记录每次生成路径、检查结论、问题和修正。`sha256` 用
Python `hashlib.sha256(Path(path).read_bytes()).hexdigest()` 计算，检查最终压缩图后填写。
脚本验证格式和证据引用，不替代语义核验或视觉审核。
